Lyra is a self-hosted web proxy built from several cooperating services. At the heart of it are three core runtime components — **Mochi** (Rust reverse proxy), **Nuru** (Rust WebSocket tunnel), and **Folio** (TypeScript + WASM service worker) — all sitting behind a **Caddy** reverse proxy that handles TLS termination and load balancing. Understanding how these pieces hand off work to each other is the foundation for operating, debugging, and extending Lyra.

## Request Flow

Lyra handles two distinct types of traffic: standard HTTP/S web requests routed through the service worker and Mochi, and WebSocket/TCP tunneling routed through Nuru.

### Web Requests (HTTP/HTTPS)

```
Browser
  │
  ▼
Caddy (443/80) ── TLS termination, routing
  │
  ▼
Lyra Frontend (Node.js, :4444)
  │
  ▼
Folio Service Worker (in-browser, /b/ path)
  │  intercepts all fetch/XHR/WebSocket calls from proxied pages
  ▼
Caddy Load Balancer (:4000) ── distributes across Mochi workers
  │
  ▼
Mochi Worker (:4100+i) ── reverse proxy, caching, rewriting
  │
  ▼
Origin Server (public internet)
```

When a user navigates to a proxied URL, Folio's service worker intercepts the `fetch` event, encodes the target URL into a Mochi-routable path, and forwards the request to Mochi. Mochi fetches the resource from the origin, rewrites HTML and CSS responses to proxy all embedded URLs, and returns the result. Static assets are served from Mochi's multi-tier cache on subsequent requests.

### WebSocket / TCP Tunneling

```
Browser
  │
  ▼
Caddy (:443) ── WebSocket upgrade
  │
  ▼
Caddy Load Balancer (:4001) ── distributes across Nuru workers
  │
  ▼
Nuru Worker (:4200+i) ── Wisp v2 server
  │
  ▼
TCP/UDP destination (public internet)
```

For WebSocket connections and direct TCP/UDP tunneling, the browser connects to Nuru using the [Wisp v2 protocol](https://github.com/MercuryWorkshop/wisp-protocol). Nuru multiplexes any number of streams over a single WebSocket connection, forwarding each to its TCP or UDP destination.

## Port Layout

All services bind on localhost and are exposed only through Caddy's reverse proxy. Do not expose these ports directly to the internet.

  <Accordion title="Public-facing ports (Caddy)">

    | `80` | Caddy | HTTP redirect to HTTPS |

    | `3478` | eturnal | STUN/TURN for WebRTC |

## Adaptive Capacity

All Rust services — Mochi and Nuru — share the `adaptive-capacity` crate. Instead of static thread pools or fixed connection limits, every service uses **`AdaptiveGate`** semaphores whose limits are continuously rebalanced by a background task.

Every 2 seconds, the rebalancer reads available RAM from `/proc/meminfo` and the system one-minute load average, then adjusts each gate's permit limit upward or downward within pre-computed min/max bounds:

- **Memory pressure** — if available RAM shrinks, permit limits are reduced so in-flight work doesn't exhaust memory.
- **CPU load** — gates classified as `Workload::Cpu` or `Workload::Mixed` also factor in normalized CPU load, while `Workload::Io` gates are bounded only by memory.
- **Graduated growth** — limits can be cut immediately but grow only by one quarter of the gap per tick, preventing oscillation.

<Info>
  You can observe the current gate state for Mochi at any time by calling `GET /metrics` on any Mochi worker. The response includes `capacity.active`, `capacity.limit`, `capacity.minimum`, `capacity.maximum`, `capacity.peak`, `capacity.waits`, and `capacity.rejected` fields for the main request gate.
</Info>

This design means Lyra automatically uses more of your server when load is light and backs off gracefully under memory pressure — without operator intervention and without requiring manual tuning of concurrency knobs for each deployment size.
